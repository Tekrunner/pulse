VERIFIED BASIS

Choose Observable Framework provisionally

Bind it only after a small production-path and exit-seam pilot.

The maintenance concern is real for both candidates. Each moved from active feature development to sparse, concentrated maintenance, and both latest npm releases are five to six months old. [1][2][3][4] Evidence created a new open-source next snapshot on 2026-08-17, but one unreleased commit is not yet a maintenance record. [8]

Neither fails Pulse’s hard gates. Observable leads because its visual boundary can remain ordinary JavaScript returning DOM/SVG. Evidence makes arbitrary reusable visuals Svelte components and extends framework coupling into preprocessing, source commands, and generated manifests. [13][14][17][18]

Rejection condition: if the pilot cannot move the same visual and data client into a minimal Vite page unchanged, reject Observable.

Current implementation reality

HIGH Observable’s reusable visual boundary is smaller: a JavaScript function can return a DOM element from an ordinary module. Page reactivity and cleanup remain Observable-specific. [10][12] Portability requires plain-data inputs, standard DOM/SVG outputs, and no runtime globals or special protocols. [13]

HIGH Evidence offers the same visual freedom through a .svelte component. Core 40.1.8 uses a Svelte/SvelteKit compiler boundary and Evidence-specific preprocessing/runtime packages. [14][16][19]

QUALIFIED Both examined versions integrate DuckDB-WASM 1.29.0. [21][24] Evidence’s extra machinery is useful, but issue evidence identifies large-Parquet load risk and a narrow base-path preprocessing defect. [19][20]

UNVERIFIED COMPARISON No controlled current performance comparison was found. Bundle size, WASM startup, time to first readable visual, and deep-link behavior remain pilot questions.

Lock-in and failure modes

Observable

Lock-in concentrates in reactive Markdown, implicit imports, special protocols, generated paths, and convenience SQL registration. [13] Keep these in disposable page adapters.

Evidence

Lock-in spans Markdown, Svelte preprocessing, Evidence packages, source commands, manifests, path rewriting, and the generated template. [16][17][18] Keep Parquet; own the manifest.

Both are permissively licensed and forkable, but a short frozen-release migration is more credible than maintaining either full stack as a fork. [16][23]

Verdict and overturning conditions

Pick: Observable Framework, provisionally. Runner-up: Evidence Core.

Observable is safer only if less of Pulse belongs to Observable. Evidence wins if Pulse consciously adopts Svelte as the long-term visual model and values packaged data machinery over framework-neutral portability. It also wins if next becomes the released default, sustains public maintenance, documents the Core/Studio contract, and modernizes current coupling.

Strongest argument against the pick: no stable Observable release with new features has shipped since November 2024; recent activity is sparse and concentrated, and strategic attention moved elsewhere. [1][3][5][6]

Recommendations

  1. Run the same bounded pilot in both. Real GitHub Pages subpath, one nested report, one interactive SVG, and identical Parquet.
  2. Own the portable seam. Pulse manifest plus an explicit dataClient.ts for DuckDB initialization, registration, parameterized queries, errors, and teardown.
  3. Keep visuals framework-neutral. Plain data in; standard DOM/SVG out; no visualization library or framework runtime package.
  4. Run an exit drill. Move the visual and data client unchanged into minimal Vite. Reject leakage.
  5. Make privacy structural. Separate roots, credentials, jobs, and artifact scans; public builds have no private access.
  6. If Observable passes, pin 1.13.4 and resolved dependencies; ban unversioned imports. [3][13]
  7. If Evidence wins, adopt Svelte consciously and enforce base-path-safe href/src. [14][19]
  8. Re-evaluate Evidence next if released before implementation. [8]
