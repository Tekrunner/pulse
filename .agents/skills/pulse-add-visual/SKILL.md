# Add a Pulse visual

Treat this as a staged design-to-implementation workflow. The design is made on a Design canvas and the approval is human; pause at approval rather than silently crossing it.

1. Read [references/workflow.md](references/workflow.md). Verify the story, every report-facing dataset contract, and its corresponding published Parquet. If any contract or Parquet is absent or fails `pulse verify`, stop and route that prerequisite to `pulse-add-dataset`.
2. Write a self-contained design brief from `assets/claude-design-prompt.md`, supplying the actual story, contracts, Parquet paths, `docs/visual-contract-v1.md`, `site/design/tokens.css`, `site/design/visual-language.md`, and relevant shared styles. Then make the design yourself on a Design canvas: the Artifact tool's `quickstart` with `intent: "design"`, the Design type it names, and that type's instructions, with the brief as the request. Design on Pulse's tokens and shared vocabulary, not an organization-default design system; load real rows as an uploaded data script built from the published Parquet; give working controls to the artboards that have them. Make the content and visual decisions from the questions and data; do not preselect chart types or simplify the request.
3. Package the canvas files, decisions, Visual Contract v1 declarations, real fixtures, rationale, and local assets with `assets/handoff-manifest.json` (canvas URL under `remote_assets`, the data script under `design_only_support`), then run `scripts/handoff_gate.py inspect`. Incomplete output remains at the design stage.
4. Give the human the canvas link. Pause for explicit human approval. Record the approver and narrowly permitted implementation changes with `scripts/handoff_gate.py approve`. The resulting digest makes the complete handoff binding. Any later digest mismatch or unrecorded design deviation returns to human/design review.
5. Produce the coding handoff from `assets/implementation-brief.md`. The coding agent preserves approved copy, layout, styling, geometry, behavior, and states while replacing fixture rows with validated query rows. It must not port prototype runtime, representative data, design-only support files, or remote assets.
6. Implement and register using [references/registration.md](references/registration.md). Prove one figure end to end before expanding. Use `assets/numeric-boundary-harness.mjs` with actual pinned stored, browser-query, and displayed observations for every distinct conversion path. That evidence is a one-time record at its `dataset_revision`; the report's browser spec derives its expectations from the served data and never repeats the pinned displays (`AGENTS.md` › Tests over published data).
7. Review with `assets/fidelity-checklist.md` and [references/verification.md](references/verification.md). Every requirement needs behavior evidence or a recorded rendered inspection at matching desktop, narrow, state, and zoom/reflow views. Unexplained differences or unchecked items keep the work open.

Ask before proceeding without a design canvas or human approval, changing approved presentation or behavior beyond the permitted-change record, adding dependencies or shared design roles, changing a contract major, or weakening accessibility, isolation, lineage, or shared-client ownership.

Never ask the coding agent to design or simplify the visual. Visuals receive only validated plain rows plus display and provenance inputs and return ordinary DOM/SVG. They own no SQL, DuckDB, Parquet/storage paths, routes, framework globals, or shared resources; use no chart library. Under the layer contract in `AGENTS.md` a visual draws from the rows and display inputs it is handed and nothing else: palettes, breakpoints and geometry are presentation constants and belong here, while membership, classification and identity are not, and a value derivable from the supplied rows is derived rather than listed.
